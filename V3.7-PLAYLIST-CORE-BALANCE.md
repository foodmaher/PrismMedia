# Version 3.7 event playlist refresh and core balance

## Live playlist updates

YouTube playlists are re-queued through the official IFrame Player API only
when:

- the current playlist video reaches the `ENDED` state;
- the user selects **Next**; or
- the user selects **Previous**.

There is no periodic playlist timer. A playlist therefore creates no new
network or JavaScript work while its current video is playing. Re-queueing the
same playlist ID asks YouTube for its latest contents, allowing videos added on
another device to appear without restarting ETS2/ATS or PrismMediaClient.

## CPU scheduling

PrismTextureStreamerFB is loaded inside the game process. Applying a process
affinity mask to the plugin would also constrain ETS2/ATS, so version 3.7 does
not change process affinity.

Instead, the Present hook samples its current logical processor once every
eight frames. Every two seconds it selects three logical processors least used
by that render thread. Only plugin-owned WGC, compatibility-capture and native
media worker threads receive these processors as Windows
`SetThreadIdealProcessor` hints. They are preferences, not hard affinity, and
Windows can move the threads whenever necessary.

The separate PrismMediaClient/WebView2 helper starts in the Windows
**Below Normal** priority class so normal-priority game work wins CPU
contention. This does not change playback resolution, hardware decoding or the
game's scheduling priority.

## Environment-volume cost

The full environment estimator is capped at 20 updates per second. Previously,
only its helper-message delivery was limited to 20 Hz while speed smoothing,
wheel checks and configuration locking could still happen once per game frame.

The settings mutex is now acquired with a non-blocking `try_lock`; a busy lock
skips that update rather than stalling the render thread. Media gain delivery
continues to use `PostMessage`, so the game never waits for PrismMediaClient.
The in-game Environment-Aware Media Volume panel reports the estimator's
smoothed microseconds per executed update.

The helper audio timer now treats unchanged gain and pan as no-ops. Audio
session COM writes run only after a value change, after a new WebView2 audio
session appears, or during a five-second health check. This keeps dynamic
volume responsive while removing the former ten-times-per-second rewrites
when the truck and camera state are steady.

## Diagnostic logs

Two bounded, asynchronous diagnostic logs are written beside the game
executable:

- `PrismTextureStreamerFB.log` records plugin startup/shutdown, telemetry state
  changes, media commands, helper launch results, ten-second performance
  summaries and selected background logical-processor hints.
- `PrismMediaClient.log` records WebView2 startup, media source selection,
  YouTube playlist refreshes and YouTube playback errors.

Both writers run below normal priority, rotate at 4 MiB and retain one `.old`
file. Game/render threads never perform disk writes. The native queue uses a
non-blocking lock and drops a diagnostic event instead of stalling gameplay if
the queue is momentarily busy.
