# PrismTextureStreamerFB 3.12.1 - Audio Fix V2

This revision targets the silent-audio condition where Spotify reports that it
is playing while the Windows WebView audio session is present, at 100% master
volume, and not muted.

## Changes

1. **Fail-open Web Audio interception**
   - `www/adaptive-audio.js` no longer reroutes a page-owned connection to
     `AudioContext.destination` while the adaptive low-pass feature is disabled.
   - Spotify/DRM audio therefore keeps Chromium's native graph unless filtering
     is explicitly requested.

2. **WebView2 core mute handling**
   - The helper explicitly sets `CoreWebView2.IsMuted = false` at startup,
     successful navigation, and Spotify play requests.
   - The log now reports both `IsMuted` and `IsDocumentPlayingAudio` so a future
     log can distinguish "Spotify UI says playing" from "WebView2 is actually
     producing audio".

3. **All-output WASAPI discovery**
   - Adaptive audio no longer assumes the Windows Multimedia default endpoint.
   - Every active render endpoint is enumerated, which covers per-app routing,
     virtual mixers, Bluetooth/USB outputs, and other non-default devices.
   - Session-baseline diagnostics now include the Chromium process ID and the
     endpoint ID.

4. **Previous 3.12.1 hotfixes retained**
   - Cursor alignment/visibility changes remain in this source tree.
   - The earlier CORS-safe media routing and audio-session master/channel fixes
     are retained.

## Expected new log lines

Examples:

- `WebView2 core audio state (...): muted=False, documentPlaying=True.`
- `WebView audio session baseline: pid=..., endpoint=..., master=1.000, muted=False, channels=2.`
- `Attached adaptive processing to ... WebView audio session(s) across active render endpoints.`
- `Web Audio destination hook installed in fail-open mode.`

If Spotify reports `playing` but `documentPlaying=False`, the remaining problem
is upstream of Windows volume/routing (for example protected-media/DRM playback)
rather than the session mixer.
