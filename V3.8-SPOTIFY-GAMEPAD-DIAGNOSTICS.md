# Version 3.8 Spotify, gamepad and render diagnostics

Version: `3.8.1-gamepad-fallback-hotfix`

## Spotify experiences

- **Embed (recommended):** lowest CPU/GPU impact, no account login, and the
  same stable capture path as earlier releases. Spotify does not expose native
  skip controls to its embed API, so Next/Previous cycles the saved Spotify
  links.
- **Full Web Player (experimental):** loads the normal Spotify website in the
  existing WebView2 helper. Its dedicated profile preserves login and site
  data. Native page controls are used for Play/Pause, Next, Previous, Mute and
  Volume, with Windows media keys as a fallback if Spotify changes its page
  markup.

Use **Open Spotify login / controls** to interact with the normal page, then
use **Return helper to silent mode** before driving. **Clear Spotify
login/session** clears the helper's persistent browsing profile.

Full Web Player is deliberately optional. It uses more memory and GPU/CPU time
than Embed, and protected media/compositor behavior can vary by driver and
WebView2 version. If the GPS becomes pink, use Embed and attach both logs.

## Gamepad media bindings

Enable gamepad controls under **Media Hotkeys**. Choose automatic controller
selection or pin controller 1-4, then set an axis/trigger threshold. Each media
command has a modifier and an input. Available inputs include face buttons,
D-pad directions, stick clicks, both stick directions, triggers and bumpers.

XInput is preferred. If a pinned XInput slot is unavailable, the plugin now
searches the remaining slots instead of disabling controls. If no XInput slot
exists, PlayStation and generic controllers are also polled through the Windows
joystick API. Connected polling runs at approximately 60 Hz; when no controller
is found it backs off to 2 Hz to avoid needless CPU work.

Steam Input can intercept the physical device so neither in-process backend can
see it. If the log reports no connected controller, open the game's Steam
properties, set **Controller > Override > Disable Steam Input**, reconnect the
controller and restart the game. This was the confirmed fix on the reported
system.

Defaults:

- RB + A: Play/Pause
- RB + right stick right/left: Next/Previous
- RB + B: Mute
- RB + right stick up/down: Volume Up/Down

The plugin does not consume the controller event, so ETS2/ATS continues to see
the same input. Choose chords that do not interfere with important driving
bindings. The diagnostic log records the selected controller number, backend
and every media command that fires.

## Diagnostics

`PrismTextureStreamerFB.log` now records:

- game texture redirect and D3D11 dynamic-target creation;
- capture backend start/stop, size changes and WGC staging-ring pressure;
- invalid buffers/dimensions and D3D11 `Map` failures/recovery;
- source stalls and recovery;
- a lightweight 20-point magenta/pink frame classifier once per second; and
- a render summary every ten seconds.

`PrismMediaClient.log` records WebView2 initialization, navigation result,
process failure, Spotify DOM/media-key routing, persistent-session actions and
soft CPU-hint application. Both logs remain beside the game executable and
use bounded asynchronous writers.

## CPU and FPS monitor

The FPS-loss number is smoothed over approximately 2.5 seconds. It estimates
the render-thread time directly removed by the texture upload; it cannot turn
decoder/GPU contention into an exact FPS count.

The collapsed logical-processor list updates from low-overhead two-second
samples:

- red: the game's Present/render thread was observed there;
- green: an in-process plugin worker was observed there;
- yellow: both were observed there; and
- grey: neither sampled path was observed there.

This is intentionally not an ETW profiler and does not claim to see every game
engine or separate WebView2 process thread. Plugin workers and the helper use
soft ideal-processor hints; no game or helper affinity mask is restricted.
